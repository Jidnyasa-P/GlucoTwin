# Data documentation

**Everything committed to this repository is SYNTHETIC.** No real patient data is stored here.

## Datasets
| Name | Population | Role | Access / terms | In repo? |
|---|---|---|---|---|
| Synthetic cohort (`scripts/generate_synthetic_data.py`) | 100 simulated type-2-diabetes-like patients, 14 days, 15-min CGM | Training, evaluation, demo | MIT (generated by this code), seed 2026 | Regenerated locally into `data/generated/` (git-ignored) |

## Schema (`readings.csv[.gz]`)
| Column | Meaning |
|---|---|
| `patient_id` | `SYNTH-###` (synthetic) or `SHT2-<id>` (ShanghaiT2DM adapter) |
| `timestamp` | ISO-8601 UTC, 15-minute grid |
| `glucose_mg_dl` | CGM glucose in mg/dL; empty = missing reading (kept missing, never imputed) |
| `steps`, `heart_rate_bpm` | SYNTHETIC wearable context, generated independently of glucose; UI demo only, **not model inputs** |
| `source` | `SYNTHETIC` or the real dataset label; carried through to the dashboard |

`profiles.csv`: `patient_id, age_years, sex, bmi, diabetes_years, hba1c_prior_pct, diagnosis, medications, source`.
`hba1c_prior_pct` represents a lab drawn *before* the monitoring window (it is not computed from the scored period).

## How the synthetic data are made (and why they cannot validate physiology)
Baseline glucose + meal-driven excursions (gamma-shaped absorption) + a dawn bump + autocorrelated noise + sensor noise; sensor gaps (about 3% of readings missing, including multi-hour dropouts).
Consequences you must keep in mind:
* Meals follow a **fixed daily schedule with jitter**, so time-of-day features help *by construction*.
* A patient's prior HbA1c reflects their baseline glucose *by construction*. Any gain from static fields is not evidence of a real relationship.
* The missingness rate is a generator parameter, not a measured device property.

## Using real data locally (unverified path)
1. Download ShanghaiT2DM yourself from its figshare record (cite Zhao et al. 2023; **check the licence on the record**).
2. `pip install -r requirements-real-data.txt` if the files are Excel.
3. `python scripts/prepare_real_data.py --raw-dir <folder> --out data/real_prepared`, then inspect the printed summary (unit, time zone, columns, counts; the paper reports 112,475 CGM points for 100 patients).
4. `python scripts/train.py --data data/real_prepared --out models_real` and `python scripts/evaluate.py --data data/real_prepared --models models_real`.
The adapter encodes **assumptions** about file layout (it could not be tested on the real files here), assumes `Asia/Shanghai` timestamps, refuses ambiguous CGM units, and groups all recordings of a person under one patient id so patient-level splits stay leak-free.
Never commit or share the raw or prepared real data. Report real-data results separately from synthetic ones.
